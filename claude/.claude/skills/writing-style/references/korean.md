# 한국어 산문 카탈로그

SKILL.md 한국어 레이어의 세부 규칙. 한국어 산문(PR 본문, 이슈, 설계 문서, README, Slack 초안, 리뷰 코멘트)을 쓰거나 고칠 때 SKILL.md와 함께 읽는다. 우선순위는 SKILL.md가 정한다.

## 산문 다듬기

### 문장

- **종결어미**: 개요, 배경, 목표는 해요체. 절차, 단계 목록, 체크리스트는 "~한다"체. 개요는 부드럽게, 절차는 건조하게. 해요체 안에서는 "~죠", "~고요", "~거든요"를 가끔 섞어 리듬을 만들고, 짧은 반문("왜냐고요?")도 개요와 배경에서 드물게 허용한다. 격식 등급은 오가지 않는다(해요체 문단에 "~한다" 문장을 섞지 않는다).
- **괄호 부연 최소화**: 괄호는 그 값이 독자에게 무엇인지 알려줄 때만 남기고, 구현 내막(파생 출처, 멱등성)은 뺀다. `라우터 변경 없이(round-robin 유지)` → `라우터 변경 없이`, `(Pipeline pkid에서 파생)` → `(PipelineJob의 mid)`. 파일 경로는 조사로, 부연은 수식으로 푼다: `` `X`(models/a.py) 추가 `` → `` models/a.py에 `X` 추가 ``, `` `from_value`(파싱) `` → `` 파싱하는 `from_value` ``. 영어 병기 괄호는 첫 등장 1회만 쓰고 이후는 한글만 쓴다.
- **문장 길이를 변주한다**: 같은 길이의 문장을 줄줄이 찍어내지 않는다. 단문만 이어지면 인접한 것을 연결어미로 묶어 복문과 섞고, 긴 문장 뒤에는 짧은 문장을 둔다. 균일한 리듬 자체가 AI 신호다(측정 결과 100자 이상 장문은 사람 글에 11배 더 많다).
- **짧은 두 문장은 잇는다**: `논의했어요. 하지만 ~` → `논의했지만, ~`.
- **불필요한 주어를 뺀다**: 문맥이 주어를 알려주면 뺀다. "소비자"(consumer) 같은 직역 주어는 "호출부"로 바꾸거나 생략한다. `소비자가 도메인 enum으로 옮겨가 안 쓰이는 메서드 제거` → `안 쓰이게 된 메서드 제거`.
- **같은 대상은 같은 말로**: `따옴표 적용`이라 쓴 다음 줄에서 `인용`으로 바꿔 부르면 독자가 다른 것으로 읽는다. 처음 고른 말로 끝까지 간다.
- **군더더기 제거**: 정확해 보이려 붙인 한정어(`부분 실패로 기록` → `실패로 기록`)와 한 문장 안에서 겹치는 말(`수집 리전을 ... 수집 대상에서 빠져요`의 앞 `수집`)은 지워도 성립하면 지운다.
- **확인한 사실만**: 원인을 짐작해 나열하지 않는다. `권한이 없거나 API가 꺼진 리전 하나 때문에` → `API 에러가 발생한 리전 하나 때문에`. 원인이 둘 이상이면 둘 다 확인했는지 되묻는다.
- **담백하게**: 강조용 따옴표, 비유어("함정" → "부분"), 비유 동사구(`코드가 움직이면 낡으니` → `코드가 변경되면 outdate되니`)를 평문으로.

### 어휘

- **코드 개념과 UI 요소는 영어 원어**: IT 회사 독자에게 한글 명사구 직역이 더 어색하다. `응답 조기 반환` → `early return`, `세는 값` → `counter`, `키 후보` → `partition key 목록`, `경로 형식` → `resource name 포맷`, `표` → `table`, `선택 상자` → `select`.
- **완곡한 동사 대신 실제로 한 일**: `정리했어요`, `대응했어요`, `보고`는 무엇을 했는지 알려주지 않는다. `계속 Ingest하도록 정리했어요` → `구현했어요`, `에러로 보고` → `에러로 처리`, `줄였어요` → `간결하게 바꿨어요`, `다뤄서` → `파싱해서`, `합쳤어요` → `통일했어요`.
- **체감 대신 상태 서술**: 독자의 체감("안 보여요", "남은", "붙었다는")이 아니라 대상의 상태를 적는다. `문서에 안 보여요` → `문서에 명시되지 않았어요`, `URL에 남은 project` → `URL에 명시된 project`, `experiments에도 붙었다는` → `experiments에도 해당한다는`. 코드가 UI 상태를 바꾸는 경우는 피동이 자연스럽다: `select는 숨는데` → `select는 숨겨지는데`.
- **구어 동사는 서술형으로**: `나면` → `발생하면`, `나가면` → `배포되면`, `부르면` → `호출하면`, `잃어요` → `유실돼요`, `못 봐서` → `조회하지 못해서`, `찍히게` → `기록되게`. 지시어 "이 X"는 "해당 X". 극존칭은 필요 없다(`제안하신` → `제안해준`).
- **제안은 권유형으로**: 대안 문장은 "~하는 쪽이 좋겠어요"로 맺는다. `~쪽이 진단 정보가 더 많아요` → `~쪽이 더 좋겠어요`.
- **참조는 링크로**: 이슈 번호, 페이지명은 실제 링크나 멘션을 건다.

### PR 본문 구조

- **불릿은 한 항목 한 메시지**: 파급효과를 덧붙인 둘째 문장과 "이 문서를 정리한다" 같은 메타 항목을 지운다. 독자가 궁금해할 것 같아 미리 답해 둔 문장부터 지운다.
- **부모 불릿은 무엇을 바꿨는지 한 줄, 조건과 이유와 세부는 하위 불릿**: 셋 이상을 쉼표로 늘어놓지 않고, 마침표로 이은 둘째 문장도 하위로 내린다. `콤마 구분 다중 리전 파싱 지원, 빈 값이면 기동 시 ValueError` → 하위 2줄. `entrypoint.sh의 인자에 따옴표 적용. 따옴표가 없으면 shell이 인자를 쪼개요` → 적용은 부모, 이유는 하위.
- **Changes는 명사형으로 맺는다**: "추가해요/제거해요" 대신 "추가/제거/변경/유지". 개요와 배경은 해요체 유지. 제목 구실을 하는 자리(헤딩, 표 헤더, 불릿의 굵은 머리말, 단계 이름)도 본문 문체와 무관하게 명사로 끝낸다(`무엇을 손보나요` → `교정 예시`, `시작하는 방법` → `시작 방법`).
- **Changes에 검증 결과를 쓰지 않는다**: `(전체 212개 통과)` 같은 실행 결과와 별도 Validation 섹션은 넣지 않는다. 테스트 추가는 변경이라 불릿으로 쓸 수 있지만 `테스트 추가: 리전 파싱, 실패 격리, 전체 실패 판정` 같은 콤마 체인은 금지.

## AI스러움 패턴

발견하면 그 문장을 재작성한다. 빈도 조건이 붙은 패턴은 그 빈도를 넘을 때만 고친다. 9번부터는 외부 카탈로그(KatFishNet ACL 2025, DaleSeo/korean-skills, epoko77-ai/im-not-ai, Turtle-Hwan/im-ai-copyeditor)와 대조해 업무 산문에 나타나는 것만 선별했다. 출처끼리 충돌하면 측정 근거가 있는 쪽을 따른다. 링크는 repo README의 참고 저장소 목록에 있다.

1. **연결어미 뒤 콤마 과다**: ~고, ~며, ~지만, ~해서 뒤에 반사적으로 콤마를 찍지 않는다. `큐를 확인하고, 잡을 제출하고, 결과를 기다린다` → `큐를 확인하고 잡을 제출한 뒤 결과를 기다린다`. 콤마를 빼면 어색한 조사가 드러나니 같이 본다: `코드에 하나로 고정하고 있어, 다른 리전은` → `코드에서 하나로 고정하고 있어서 다른 리전은`.
2. **중첩 hedging**: 사실이면 단정하고, 불확실하면 조건이나 근거를 붙인 한 겹으로 줄인다. `성능이 개선될 수 있을 것으로 보입니다` → `성능이 개선돼요`, `문제가 될 수도 있을 것 같아요` → `동시 요청이 100을 넘으면 문제가 돼요`. 추측 종결(`~로 보인다`, `~인 듯하다`, `~로 판단된다`)을 문장마다 붙이는 것도 같은 계열이다.
3. **형식명사 남용(것/점/수/바)**: 동사로 직접 서술한다. `주의할 점은 캐시가 무효화된다는 것이다` → `캐시가 무효화되니 주의한다`, `핵심은 진입장벽이 낮다는 점에 있다` → `진입장벽이 낮다는 게 핵심이다`. `~다는 뜻이다`, `~인 셈이다` 결말은 "~다"로 직접 맺고 문서 합산 2회 이하. `~것이다` 종결 자체는 논설문의 일반 종결이라(사람이 LLM의 2배로 더 쓴다) 연속 3회 이상일 때만 일부를 "~다"로 바꾼다.
4. **접속어 연발(또한/따라서/즉/나아가)**: 논리가 이어지면 접속어 없이 읽힌다. `또한 캐시를 지운다. 따라서 재시작이 필요하다.` → `캐시도 지우므로 재시작이 필요하다.` `즉`은 문서당 2회 이하로 두고 `곧`, `말하자면`으로 바꾸거나 뺀다. 메타 진입(`이는 ~을 의미한다`, `이 점에서`, `이 말은`)은 삭제하고 본 서술로 바로 간다.
5. **기계적 나열(첫째/둘째/셋째)**: 불릿이나 문장으로 잇고, 순서가 중요하면 번호 목록. 문장 안 숫자 괄호 나열(`1) ... 2) ... 3) ...`)도 같은 계열이다. `첫째 원인은 lock이고 둘째 원인은 timeout이다` → `원인은 lock과 timeout 두 가지다`.
6. **AI 관용구**: `결론적으로`, `시사하는 바가 크다`, `주목할 만하다`, `~의 정수`, `~을 넘어서`. 결말 공식(`~할 때다`, `~할 시점이다`, `지금이야말로`), 변환 슬로건(`'수동 운영'에서 '자동 운영'으로`, `X을 넘어 Y로`), 거창한 도입(`오늘날 빠르게 변화하는 시대에`, `바야흐로`)도 같은 계열이다. 삭제하거나 구체 사실로 바꾼다: `이 결과는 시사하는 바가 크다` → `이 결과로 X 가설이 기각된다`, 슬로건은 무엇이 어떻게 바뀌는지 평서로.
7. **직역 개념어와 명사 압축**: 개념어 직역(`집행 장치` → `규칙 반영 체계`, `소비처` → `참조하는 문서들`, `단일 정본` → `원본 문서`), 명사 압축(`주기 재검증` → `주기적인 재검증`, `위반 패턴` → `규칙 위반 패턴`), 직역 동사(`적중을 만들` → `적중률을 높일`), 빼도 통하는 직역 군더더기(`인자 확장에 따옴표 적용` → `인자에 따옴표 적용`). `~적 N` 추상 체인(`전략적 함의` → `전략 차원의 의미`, `실천적 기반` → `실천 토대`)은 한 문서에 3회 이상이면 풀어 쓰고, `-성`, `-화` 남발도 동사와 형용사로 되돌린다(`효율화를 달성해요` → `효율을 높여요`).
8. **행동 압축어**: 업계 표준 용어라도 한국어 문장에서는 그 용어가 가리키는 행동을 쓴다. 코드 식별자와 작성자 용어 인용은 예외.
   - `fail-fast가 필요해요` → `ENV가 없으면 초기에 바로 실패시키는 조치가 필요해요`
   - `의도한 이연이면` → `의도한 거라면`, `주석을 현행화하면` → `주석을 최신 사실에 맞게 고치면`, `스모크 테스트를 권해요` → `테스트를 추가하면 좋겠어요`
   - `테스트가 None 기대로 뒤집혔어요` → `assert가 []를 확인하다가 is None을 확인하도록 바뀌었어요`. 판정의 변화는 어떤 값에서 어떤 값으로 바뀌었는지 그대로 쓴다.
   - `실측했어요` → 재어 봤으면 `실제로 측정했어요`, 눈으로 봤으면 `직접 확인했어요`. 둘 중 실제로 한 쪽을 쓴다.
   - `접다`, `접히다`는 UI collapse 비유라 분량을 줄인 방법이 사라진다. `코드 블록을 접어 분량을 줄였어요` → `코드 블록을 자리 표시로 바꿔 분량을 줄였어요`, `섹션을 접어도` → `섹션을 축소해도`.
9. **번역투 조사**: 영어 전치사를 조사구로 직역한 형태. 동사에 직결하면 짧아진다.
   - `~에 있어서`는 1회만 나와도 결정적: `운영에 있어서 중요한 것은` → `운영에서 중요한 것은`
   - `~에 대해`는 목적격으로: `이 문제에 대해 논의해요` → `이 문제를 논의해요`
   - `~와 관련하여/관련된`: `보안과 관련하여 강화` → `보안을 강화`, `배포와 관련된 설정` → `배포 설정`
   - `~에 기반하여/바탕으로`: `메트릭에 기반하여 판단` → `메트릭으로 판단`
   - `~을 위해` 남발: `성능을 위해 도입` → `성능을 높이려고 도입`
   - `~를 통해`는 한 문단 3회 이상일 때만 `~로`, `~해서`로 분산한다. 개별 출현은 자연스럽다(비번역 한국어가 번역문보다 2배 더 쓴다).
   - 이중 조사(`~에서의`, `~으로의`, `~로부터의`)는 절로 푼다: `큐에서의 대기 시간` → `큐에서 기다리는 시간`
10. **영어식 피동과 잉여 동사**: 행위자가 있으면 행위자를 주어로 세운다.
    - `가지고 있다`(have 직역): `강한 경쟁력을 가지고 있어요` → `경쟁력이 강해요`
    - 이중 피동 `~되어진다`는 비문: `판단되어진다` → `판단된다`, 가능하면 능동으로. `쓰여진` → `쓰인`, `보여지는` → `보이는`
    - `~에 의해`: `스케줄러에 의해 실행된다` → `스케줄러가 실행한다`
    - `이루어지다/만들어지다`: `합의가 이루어졌어요` → `합의했어요`
    - 잉여 진행형 `~고 있다`: `이 기능을 지원하고 있어요` → `이 기능을 지원해요`. 진행 중이라는 사실이 정보일 때만 유지.
11. **추상 주어 + 만능 동사**: 사건이나 개념을 주어로 세우고 `가져오다/보여주다/제공하다/만들다`로 서술하는 영어식 통사. 구체 주어로 돌리거나 부사구로 푼다. 의인화(`기술이 묻는다`, `시대가 요구한다`)도 같은 계열. `이 변경은 성능 개선을 가져와요` → `이렇게 바꾸면 성능이 좋아져요`, `이 지표는 병목을 보여줘요` → `이 지표를 보면 병목이 드러나요`.
12. **영어식 잉여 표지(-들, 해당, 대명사)**: 수량사나 수식어가 이미 복수를 알려주면 `-들`을 뺀다(`많은 사용자들이 기능들을 요청` → `많은 사용자가 기능을 요청`). 지시관형사 `해당/본/동`은 `이`로 바꾸거나 뺀다(`본 문서` → `이 문서`). `그것은/이것은` 반복은 생략하고 바로 서술한다.
13. **균형 회피 어휘**: `양쪽 모두 일리가 있다`, `장점도 있지만`, `신중하게 접근해야 한다`, `균형 잡힌` 같은 양면 제시로 판단을 피하지 않는다. 한쪽을 단언하거나 조건으로 가른다: `두 방식 모두 장단점이 있어요` → `쓰기가 많으면 A, 읽기가 많으면 B가 나아요`. 설계 문서와 리뷰 코멘트에서 특히 잦다.
14. **대구 공식 연쇄**: `A인가, B인가`, `A가 아니라 B`, `A라기보다 B` 평행구를 잇달아 쓰는 형태. SKILL.md 대조 부정문 금지의 변형이며 부정 대구는 AI 대 사람 밀도 9.2배로 가장 강한 신호다. 연쇄 중 하나만 남기고 나머지는 직접 단언으로 바꾼다. 사실 정정 한 번(`원인은 lock이 아니라 timeout이에요`)은 예외. 격상 틀도 같은 계열: `중요한 것은 순서예요` → `순서가 중요해요`, `빠를 뿐만 아니라 저렴해요` → `빠르고 저렴해요`.
15. **동의어 이중 수식**: `중요하고 핵심적인 역할`, `지속적이고 꾸준한 노력` → 수식어 하나만 남긴다.
16. **문장 군더더기(김정선 계열)**: 없어도 뜻이 통하면 뺀다.
    - `-의` 연쇄: `회사의 성장의 요인` → `회사가 성장한 요인`
    - 군더더기 `있다`: `발표가 있을 예정이에요` → `발표할 예정이에요`, `벽에 걸려 있는 그림` → `벽에 걸린 그림`
    - `-ㄹ 수 있는` 수식: 가능성이 요지가 아니면 뺀다. `성공할 수 있는 가능성` → `성공할 가능성`
    - 에두름: `효과가 있다고 할 수 있어요` → `효과가 있어요`
    - `~중 하나`(one of 직역): `가장 큰 문제 중 하나예요` → `손꼽히는 문제예요`
    - 이중부정: `이 방식을 쓰지 않을 수 없어요` → `이 방식을 써야 해요`
17. **사동, 시제, 관사 직역**: `-시키다` 오용은 `-하다`로(`성능을 개선시켰어요` → `성능을 개선했어요`, 진짜 사동 `모델을 학습시켰어요`는 유지). 시제 중복(`했었어야 했다` → `해야 했다`, `노력해 왔다` → `노력했다`, `지난주에 읽었던 책` → `지난주에 읽은 책`). 관사 직역(`하나의 예시로` → `예시로`, `그 어떤 말도` → `어떤 말도`). 안긴 절(`왜 실패했는가를 분석` → `왜 실패했는지 분석`).
18. **일본어투와 행정어**: 정해진 문구(법령, 계약)가 아니면 쉬운 말로. `~에 의거하여` → `~에 따라`, `금번` → `이번`, `상기` → `위`, `익일` → `다음 날`, `~에 위치하다` → `~에 있다`, `~에도 불구하고` → `~지만`, `~을 필요로 한다` → `~이 필요하다`, `검토를 요한다` → `검토해야 한다`.
19. **권고형 결말 남발**: `~해야 한다`, `~할 필요가 있다`가 결말마다 자동으로 붙는 형태. 문서에 5회 이상이면 주체를 명시한 단언(`정부는 ~를 도입한다`)이나 조건문(`~이 충족되면 ~가 가능하다`)으로 바꾼다. 개별 사용은 자연스럽다.

## 리뷰 코멘트 (인라인 코멘트와 답글)

기준은 johan이 직접 남긴 인라인 코멘트의 말투다. 짧고, 질문이 많고, 어미가 섞이고, 근거는 뒤에 한 절로 붙는다. 균일한 두 문장에 "좋겠어요"만 반복하면 기계가 쓴 것처럼 읽힌다.

### 형태

- **짧게**: 한두 문장. 절반은 한 문장이다. 관찰만 적고 결과 설명은 상대가 모를 법할 때만 붙인다. `TypeVar가 안쓰이는 것 같아요.`, `주석과 코드 불일치`, `안쓰이네요.`, `클래스 변수면 대문자일 필요가 없을 것 같아요.`
- **대안은 suggestion 블록에 한 줄 lead**: 코드로 보여줄 수 있으면 문장으로 풀지 않는다. lead는 `요렇게 갈게요.`, `P5; Simplify`, `For debugging`, `ditto;` 정도.
- **반복 지적은 `ditto;`**: 같은 지적이 다른 줄에 또 나오면 본문 없이 `ditto;`만 남긴다.
- **낮은 우선순위는 `P5;`**: 취향이나 사소한 제안은 `P5;`로 시작한다. 약한 의견은 문장으로도 밝힌다: `약한 의견이라 넘어가셔도 됩니다!`, `취향이지만 한 번 남겨봐요.`, `혹시 몰라 코멘트 남겨봐요.`, `사소한 부분이라 우선순위는 낮아요.`
- **지시어는 `요거`, `요건`, `요기`, `여기도`**: `이 부분은` 대신 `요거 어디서 주입되나요?`, `요건 migration 파일명을 달아주셔야 오해가 없을 것 같아요.`, `여긴 지우시죠!`
- **질문으로 짚는다**: 확신이 없거나 작성자 의도가 있을 법하면 단정 대신 질문. `여기 도달 가능한가요?`, `이건 왜 수정된거에요?`, `~하신 이유가 있을까요?`, `의도하신걸까요?`, `~하면 어떨까요?`, `~어떻게 생각하시나요?`, `~않을까요?`
- **근거는 뒤에 `~서요`로 한 절**: 제안이나 질문을 먼저 쓰고 이유는 다음 문장에 `~서요`, `~고요`로 붙인다. `요 변수 선언부도 좀 더 아래 선언해보는건 어떨까요? 선언부와 활용되는 부분이 멀면 가독성이 떨어져서요.`, `처리 함수도 같이 넣어줄 수 있으면 좋고요.`
- **어미는 섞는다**: `것 같아요`, `좋을 것 같아요`, `좋겠어요`, `좋겠네요`, `좋아보여요`, `필요해보여요`, `필요해요`, `부탁드려요`, `해주세요`를 상황에 맞게 고른다. 한 종류로 통일하지 않는다.
- **정리 요청은 `~하시죠`**: 명백한 삭제나 이동은 권유 명령형으로. `argparse로 빼시죠`, `여긴 지우시죠!`, `일단 ON DUPLICATE KEY UPDATE 해보시죠`, `간단하게 이야기 나눠보시죠!`
- **가벼움 표시**: `ㅋㅋㅋ`, `ㅎㅎ`, `-!`, `~`는 사소한 지적, 자기 실수, 농담에만 쓴다. 버그와 데이터 손실에는 쓰지 않는다.
- **참조는 줄 앞뒤에 링크**: `Reference:`, `Ref:`, 또는 URL 한 줄. 위치는 `L152`, `L261-L263`처럼 적는다.
- **후속은 문장으로 가른다**: `다음 PR에서 고민해보죠!`, `나중에 정식 배포되면서 재조정해보시죠.`, `추후 ~할 때 고려해도 좋을 것 같아요.` 요약 코멘트에는 머지를 막는지 밝힌다.

### 내용

- **판정 대신 제안**: 심사 어휘는 받는 사람이 방어적으로 읽는다. `일관돼요` → `좀 더 일관성있어요`, `테스트를 권해요` → `테스트를 추가하면 좋겠어요`. 작성자의 선택을 인정한 뒤 지적한다: `차단 자체는 여전히 유효하지만` → `차단 자체는 좋지만`.
- **결과를 붙일 때는 관측 가능한 증상으로**: "문제가 될 수 있어요" 대신 "api key를 찾다 500이 나요", "부팅이 실패해요", "실패 알림 지연이 4배가 돼요". 버그와 데이터 손실은 결과를 반드시 붙인다.
- **근거는 직접 확인한 것만, 확인 방법을 한 절로**: "이 파일을 지우고 돌려도 12개 테스트가 그대로 통과해서". 확인하지 않았으면 지적 대신 질문으로 남긴다.
- **동작과 PR 본문이 어긋나면**: 동작 변경을 제안하기 전에 어느 쪽이 의도인지 보고, 본문이 틀렸으면 description 수정을 요청한다.

### 답글

- 짧게 끝낸다: `네 맞아요!`, `아 맞네요.`, `반영 완료`, `수정했어요-!`, `동의합니다`. 커밋은 짧은 sha 링크로: `[c5e60ee](...)에서 삭제했어요.`
- 감탄 도입 `아하,`, `음,`, `오,`, `엇,`은 답글에서만 쓴다.
- 판단이 바뀌면 짧게 수용하고 끝낸다(`CI 단에서 막는다면 저도 괜찮은 것 같아요-!`). 조건을 다시 나열하거나 원래 지적을 변호하지 않는다.
- 동의와 한 일을 같이 쓸 때 문두의 동의 표현을 뺀다: `맞아요. ~로 옮겼어요` → `~로 옮겼어요`. 굳이 쓰면 `맞네요`.
- 받아들이지 않을 때는 판단 근거를 밝힌다: `실패해도 Pool Name을 표기하지 못할 뿐이라 재시도까지는 필요하지 않다고 판단했어요`.
- 오프라인 논의 결과는 `오프라인으로 이야기 나눴는데,` 또는 `구두논의:`로 남긴다.
- 논점이 셋을 넘으면 `Q1.`, `Q2.` 또는 `#### 소제목`으로 나누고 마지막은 대안을 묻는 형태로 맺는다.
- 프로세스 조언은 인라인이 아니라 요약 코멘트에 둔다. `추가로 말씀드리고 싶은게 있는데요`로 열고 상대에게 어떤 이득인지로 맺는다. 코드 지적과 섞으면 사람 평가처럼 읽힌다.

## 갱신 규칙

실제 출력에서 새 패턴이 잡히면 추가하고, 더는 나타나지 않는 패턴은 지운다. 항목을 바꾸면 SKILL.md post-filter의 정규식도 같이 갱신한다. 교정 내력(날짜, PR 번호, 건수)은 이 파일에 적지 않는다.
